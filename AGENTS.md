# AI task manager development

Build the approved standalone task coordinator for Claude Code and Codex CLI. Keep the reusable core independent of application-specific scripts and host integrations. The maintained plans, specifications and diagrams under docs/, configuration under config/ and acceptance inventory under tests/acceptance/ are the authoritative sources for their declared responsibilities. Read docs/readme.md and the task-relevant sections before work. Update docs/ when implementation decisions or evidence change; earlier workspace artifacts are historical. Operational records and credentials stay under ignored local storage.

Use one tracked assignment per worker, a separate Git worktree and a separate disposable fixture database. The lead coordinates and reviews; assigned workers perform substantive implementation and investigation. Delegate only assignments registered by the lead. Workers must not spawn additional workers or write to another worker's scope.

For every plan and task, follow [work-item identity and traceability](docs/implementation_plan.md#work-item-identity-and-traceability). Keep task IDs independent of parent-story membership. Show the parent story and supported acceptance criteria explicitly, record actual Linear identifiers/links when known, and preserve IDs across reparenting. Apply this rule to plans, assignments, reviews, reports and learning records; documentation-only relationship clarification does not reopen an existing implementation approval.

Every delivery plan, epic, story and task must have a confirmed record in the existing TST development project before its work is admitted. Follow [Linear delivery tracking](docs/implementation_plan.md#linear-delivery-tracking) and reuse the [verified mappings](docs/plans/linear-tracking.md). Keep Linear status, parent relationships, ownership and evidence current at each handoff and closure. Preserve obsolete work through an explicit, reversible reconciliation; never delete history or treat archived work as completed acceptance.

Custom notes are lessons-only: record a new reusable problem, correction and evidence link in a few lines. Keep task status and closure in Linear and proof in existing Git/test/review/control records. Preserve historical journals and required machine logs; stop the parallel model-authored event diary. Use existing task state for recovery and a compact pointer summary only for an actual handoff/restart.

Keep every task bounded and follow [bounded verification and evidence reuse](docs/implementation_plan.md#bounded-verification-and-evidence-reuse). Reuse applicable accepted checks and reviews. Add validation or bookkeeping only when it resolves a named acceptance gap, changed relevant input, unresolved finding or required control. Link existing records instead of creating duplicate receipts or another tracking framework. When the task's Definition of Done is met, integrate and close it, then advance to the next eligible task.

Run only relevant tests for application, skill, agent, documentation, configuration and tooling changes. Follow the linked test-selection rule: select the smallest sufficient affected checks, preserve relevant integration/regression coverage and required acceptance gates, and do not run a whole suite or matrix merely because it is available.

Read bounded log excerpts for a named question and expand only when necessary. Use one concise handoff and consume accepted results without replaying the investigation. Repeat independent review only for relevant changes, unresolved findings or required acceptance. Essential evidence remains required; optional process diaries and duplicate summaries cannot delay closure. Apply the working limits in the linked rule to every remaining plan.

Apply the [four execution gates](docs/implementation_plan.md#four-execution-gates): compact source references, review only changed or unresolved material, one task record, and a test set fixed before expansion. Use agents for substantive eligible work; do not manufacture reviews, coordination or cases to occupy capacity. Preserve agreed coverage and required final host testing.

Before authoring a document, check that its type and proposed structure are covered by current Technical Writer guidance. Follow the [unsupported document structure rule](docs/implementation_plan.md#unsupported-document-types-and-structures): if coverage is missing, tell the user and ask whether to create the template before continuing that document. Do not invent a substitute structure or treat ordinary plan approval as authorization to create a new template. Continue independent work whose guidance is established.

Keep architecture proportionate to agreed capabilities, not only the logs and tests. Every added component or abstraction must serve a named requirement or necessary safety boundary. Reuse existing mechanisms; simplify unnecessary machinery and its consumers within the affected scope. Do not add speculative frameworks or silently turn a bounded delivery into whole-project redesign.

Apply the [review-failure safeguards](docs/implementation_plan.md#review-failure-safeguards-for-every-remaining-plan) to DP03 and every later plan: preserve requirements, safeguard purposes, real independence, discovery limits, finding IDs and behavioral regressions; judge the final artifact with scope-appropriate evidence. Reference the protections within the existing task record instead of creating another checklist. Saved lessons are not implemented or validated permanent Skill Builder fixes.

Plan approval here is the sole routine execution approval for every delivery plan. It authorizes the complete scoped implementation, tests, fixes, reviews, integration, finite qualification and owned cleanup; do not ask again per task, story, test, retry or handoff. Bring a materially expanded scope back as a revised plan.

After a delivery plan is approved, continue its eligible work autonomously through handoffs, corrections, review, integration and the next task. Use bounded waits while healthy work runs. A dispatch, status response or handoff is not a stopping point. Stop only for actual completion, user pause, a material scope expansion requiring a revised agreed plan, or solely external prerequisites after eligible work is exhausted; record the exact blocker and resume action. Follow the active plan's continuation loop and reconcile existing workers before resuming. Idle capacity alone does not justify unnecessary assignments.

Use the current approved Technical Writer and Skill Builder sources. Read the announced versions before use, record their source hashes and use matching reproducible copies for validation. Every task title, description, acceptance criterion and written progress update must pass Technical Writer with the appropriate reference and Writing Style (WS) guide before publication. Apply the [application-language requirement](docs/spec_driven_development.md#application-language-and-technical-writer) to runtime output and coordinated Codex/Claude language too; hard-coded prose templates cannot replace that workflow. Scripted status/ownership fields remain governed by the execution policy. When the user announces a new skill version, audit affected work, revise only what needs changing and rerun impacted checks; preserve earlier version-bound evidence. Do not modify either source skill as part of this product build.

Use the explicitly selected Claude account in `config/execution-policy.json`. Automated invocations use the unmodified `claude` executable. An explicitly selected named configuration binds `CLAUDE_CONFIG_DIR` under the user home; the explicitly selected default `.claude` account omits that override to preserve plain-CLI login behavior. Do not inherit or fall back to another account. Verify authentication and account identity before new effects; preserve earlier account-bound evidence as historical. Authentication checks do not establish successful model execution.

Build the standalone merge engine in focused domains through its own API/CLI contract. Do not ship `merge-to-dev.sh`, a wrapper or an alias for it. Workers commit in their own branches/worktrees; one merge authority validates and integrates into the trusted configured target. Correct defective checks, sequencing, resource lifetime and attribution through versioned contracts; verify concurrency/recovery and measure commit/merge/test costs in independently authored projects. AI Index is read-only scenario evidence. No AI Index script copy may live in this repository, including ignored caches, worktrees, examples or fixtures. Keep any required immutable historical source evidence outside the product with hashes/relocation records and no import/symlink bridge. Do not change the original application or deploy production.

Enforce declared task ownership, status transitions, evidence and isolation in code. In Review supports every configured destination with authorization and destination-specific evidence. Further work on delivered issues uses a new linked issue. Activation uses one complete cutover; never run two live task-state writer systems together.

Run focused tests during development and the complete required suite for the final candidate. Retain failed attempts and distinguish blocked/not-run cases from passes. Never fabricate live provider or model evidence. Do not commit credentials, private source snapshots, machine paths or personal names in Markdown. Public pushes are authorized for reviewed code; normal-session activation and production changes remain outside scope.
