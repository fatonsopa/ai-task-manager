## Goal and specification

Extend the accepted DP03 installation so an authorized lead can reuse existing issues, exchange task changes with Linear immediately, recover missed changes, preserve human authority and request decisions without duplicate or foreign effects. Real installed commands, provider deliveries and authoritative readbacks must demonstrate the connections. Task completion, story acceptance and epic acceptance remain separate judgments.

The exact scope is the [DP04 roadmap row](../incremental-delivery-proposal.md#complete-proposed-plan-catalogue): existing-issue intake; immediate outbound and authenticated inbound synchronization; polling recovery; holds, assignments, dynamic agent delegation, decisions and lifecycle conflicts. Sources are the [Spec Driven Development document (SDD)](../../spec_driven_development.md#apply-changes-and-report-outcomes), [High Level Document (HLD)](../../high_level_document.md#real-time-linear-event-flow), [Implementation Plan (IP)](../../implementation_plan.md#required-scope), [Policy (POL)](../../policy.md), [Test Plan (TP)](../../test_plan.md), requirement inventory `config/requirements.json` and acceptance inventory `tests/acceptance/cases.json`. The original DP04 session prompt remains an execution instruction.

Keep these terms distinct: a human assignee owns Linear work; the selected application is its delegate; an integration actor performs a provider action; a local worker performs an attempt. A decision request is a real unresolved human choice, not an ordinary progress notice. An existing remote Todo issue is not automatically queued in this session.

### Implementation choices

Reuse the existing service, Core policy, authority journal, provider journal, writer, listener, scoped notifications and resource ledger. Add only the trusted selection connection and typed decision publication behavior, plus defects reproduced on the required installed paths. Reuse existing journal tables where they express the operation; a narrowly necessary additive migration must preserve old rows and pending effects. No speculative scheduler, agent framework, event diary, alternate task store or general recovery redesign is included.

For decisions, bind each request to its exact task, human recipient, approved Decision Record (DR) content and durable operation. Resolve `Waiting for Decision` to its canonical workspace/team label ID. Mention the real human creator; if the creator is an application, use the current assigned human. Verify the provider-supported mention representation and read it back before claiming a real mention. Preserve unrelated labels. Request resolution clears the managed label only when no unresolved request remains; failures between comment and label effects remain separately pending/uncertain and recover by their original identities. Routine progress cannot trigger this path. No automatic answer or human acceptance is inferred from a label change.

Dynamic delegation means resolving and revalidating the explicitly selected workspace/session connection by stable ID, with setup selection when ambiguous. Changed selection requires the already specified new logical session and current authority. Reject removed/mismatched delegate, reassignment, revoked permissions, switched account and competing claims before effects; metadata alone never proves a worker or Agent Session.
