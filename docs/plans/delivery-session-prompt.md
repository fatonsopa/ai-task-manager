# Standard delivery-session prompt

Use this prompt for each subsequent delivery plan. Replace the three bracketed inputs from the maintained roadmap and accepted handoff. Keep the delivery-specific scope, criteria and commands in the detailed plan, rather than duplicating the complete specification here. This is a planning-session instruction, not a hard-coded application content template or a new skill package.

## Prompt

Work in the AI Task Manager repository.

Delivery: [delivery ID and exact roadmap title].
Accepted baseline: [preceding delivery branch, verified commit and canonical handoff].
Existing Linear plan record: [confirmed identifier/link].

Read `AGENTS.md`, `docs/readme.md`, the accepted handoff, the roadmap row and task-relevant sections of all seven governing documents. Reconcile actual workers/processes, tasks, Git/worktrees, installed controls and retained effects. Preserve unrelated edits, accepted work, failures, original identities/deadlines and protected resources. Do not duplicate healthy assignments or reuse revoked permission as live authority.

First audit and reuse existing implementation, verified commands, their required environment and valid evidence. Read bounded sources for named questions. Distinguish supported behavior, missing connections, defects and unassessed claims. A file, passing component check or historical result cannot establish an unobserved installed workflow.

Write the detailed delivery plan through current Technical Writer Implementation Plan (IP) guidance. Define one bounded outcome epic, dependency-ordered usable stories/tasks, explicit acceptance criteria and Definitions of Done at each level. Keep task IDs independent of story membership and link parents/criteria separately. Reuse existing Linear records and create only genuinely missing work. Specify the supported command/demo and actual proof that closes each usable story. Do not fabricate counts, thresholds, commands or approval.

Identify the required workflow per deliverable. Application engineering uses the product implementation/review process; existing-skill integration verifies current version/interface and affected behavior; creating, auditing or modifying a reusable skill or agent package uses current Skill Builder's actual workflow, with Technical Writer for its documents. Do not defer applicable skill work merely because full skill packaging has a later roadmap slot. All human-readable application and coordinated-agent output must follow current Technical Writer; no separate hard-coded application prose templates. If the required document type/structure is uncovered, explain the gap and ask whether to create its template before dependent authoring; continue eligible independent work.

Select the smallest sufficient affected, regression and genuine integration checks before expansion. Every selected action needs a named acceptance obligation, changed input or observed failure. Reuse valid results with their actual source, environment and date; run broader suites/matrices only at their applicable required gate. Preserve actual independence, finding IDs, useful behavioral regressions, safeguard purposes and all thirty review-failure protections. Keep one task record and compact original-evidence links; custom notes are lessons-only. Add no optional refactor, new evidence system or process diary.

Present the detailed plan for my ONE approval before implementation, unless that exact plan is already approved. Do not ask again for established approval. Record unresolved material choices honestly. Before execution, carry the approved plan, applicable shared instructions and tracking/active-delivery changes into the execution worktree without overwriting delivered runtime/configuration or unrelated edits. Inspect this transfer once; no new manifest.

## Prove the usable path before expansion

For a delivery using managed roles, test the complete startup chain first: **sealed role → advertised tools → capture → cold verification → normal startup**. Inspect the actual tool advertisement and connected path; separate passing components do not prove the chain works. The user reports that this regression is already added and passing. Locate and reuse its actual source/environment-bound evidence when compatible; do not duplicate it or claim a new execution from that supplied report. Run affected or explicitly required fresh checks when the relevant inputs change.

Run one smallest usable path before expanding: **the lead reads the queue, selects an eligible task, then the operator starts its worker**. Confirm current authority, actual startup and task state. Prove this supported path before adding parallel workers, more roles or a larger case matrix. For changes outside managed startup, reuse matching evidence rather than launching unrelated product tests.

## Required plan and execution rules

Copy the following three paragraphs verbatim into every detailed plan produced from this prompt:

Execute the approved scope through working delivery. Reuse verified commands, their required environment and valid evidence. Every additional test or review must resolve a named acceptance criterion, changed input or observed failure. Preserve required safeguards; omit optional refactors and duplicate bookkeeping.

Complete and integrate each usable story, then continue without routine reapproval. Report accepted tasks, stories and epic criteria with denominators and percentages. Never call partial work complete.

If 15 minutes pass without delivered work or decisive evidence, explain the cause and change approach. Update me at least every 60 seconds during active work. Stop only at completion or an agreed stop condition; identify any external prerequisite and exact resume action.

Also include the startup-chain, smallest-usable-path, reporting and forced-change rules below in the detailed plan. Treat 15 minutes without delivered work or decisive evidence as a **forced change of approach**, not another opportunity to acknowledge delay. Identify the exact bottleneck and owner, stop or change the ineffective action, and state the next observable result. More preparation, passing component tests and review paperwork do not justify continuing the same approach or resetting the interval. Inspect a healthy required check's actual stage/deadline; do not kill it blindly. If an unavoidable external wait remains, identify it and advance eligible independent work. Use existing task timestamps and evidence; build no new monitoring framework.

After every completed task, story, epic criterion, review, test batch or integration, immediately report **accepted tasks x/y — %, accepted stories x/y — %, and accepted epic criteria x/y — %**, what just completed, the change since the preceding update, and the next action/blocker. Use the approved denominators and disclose an approved denominator change. Review/test completion alone does not increase accepted delivery counts; show unchanged counts honestly. Do not double-count parents/children or invent denominators before planning is complete. One compact update can satisfy completion and 60-second reporting together; do not duplicate it in another record.

## Autonomous continuation after approval

Execute the complete scoped implementation, affected checks, fixes, independent review, integration, finite genuine qualification, reporting and supported resource disposition without routine reapproval. Use current internal authority and verified environment/account/profile bindings. Do not reset history, extend predecessor deadlines or switch accounts/models/transports as a fallback.

After every result, reconcile ownership, correct the actual gap, review relevant changes, integrate/close, confirm Linear state and mark accepted plan items `DONE -` with stable IDs and dated evidence. Immediately take the next eligible task. A dispatch, handoff or status answer is not a stopping point. Delegate only substantive beneficial work or required independent judgment with actual ACK/START and isolated resources. Use bounded waits while healthy work runs; idle capacity does not justify busywork.

Continue until every approved task, story and epic criterion is accepted and owned obligations are settled or explicitly protected under the supported contract. Agreed stop conditions are completion, explicit user pause, a material scope/template decision needing agreement, or exclusively external prerequisites after eligible work is exhausted. Name the exact prerequisite, owner and resume action. Continue independent approved work where possible.

Deliver the cumulative usable increment, exact source/package/environment, supported procedure, acceptance counts/percentages, relevant genuine evidence, measurements, retained failures and resource disposition, then the next delivery's handoff. Do not implement the next delivery. Preserve publication/activation/production authority boundaries; default-branch integration requires its actual authorization. AI Index remains read-only scenario evidence without script copies or runtime coupling.
