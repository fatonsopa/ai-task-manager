# Recorded workflow recovery

Type: How-to Guide (HTG). Scope: supported DP05 owner recovery, original-effect reconciliation, partial-code continuation, explicit successors, owned retirement and reporting.

## Before you begin

Use the exact installed candidate package, original private service configuration and original installation file. Preserve the original workflow reference and operation key from the interrupted request. Live-owner observation and execution require current enrollment. Cold execution also requires the original unexpired native permission. Cold `resume` first uses separate finite observation/settlement authority for retained provider effects; this does not renew execution permission. The explicit cold stop port uses separate finite operator authority to settle an exactly recorded obligation, including after its execution grant expires or is revoked. Do not copy an installation or extend its deadline to make it eligible.

The candidate supports live-owner continuation, verified cold replacement and owned stop. Version-two successor admission and genuine expiry/revocation execution are accepted under T06/T07 and DP05-S3. Owned resource retirement and original-key readback are independently accepted under T08. Exact-event lead reporting is independently accepted under T09; use the linked reporting procedure with current finite authority. Cold recovery requires the complete original installation, store, key and controller witnesses recorded before interruption. Older rows without those facts need explicit reconciliation; this procedure does not backfill them. Ordinary run/resume retains its existing contract. Genuine S1 qualification is accepted at its recorded host/profile scope. T03 provider recovery and T04 code continuation retain their accepted component evidence. T05/S2 genuine publication, outage readback and supervisor replacement/replay are independently accepted on 17 November 2026 at that declared profile scope. Future genuine effects still need the finite admission described below.

## Steps

1. Create a private request file containing exactly the original workflow reference and operation key, with `action` set to `inspect`:

   ```json
   {"action":"inspect","workflow_ref":"<original-workflow-ref>","operation_key":"<original-operation-key>"}
   ```

2. Run the stock installed command with the original private files:

   ```sh
   aitm --config <service.json> --installation <installation.json> --json workflow recover --input <request.json>
   ```

   Expect the same workflow/task/plan/key/deadline, its attempt and step observations, and the verified owner state. No new worker or provider write is part of inspection. Stop if identity, scope, configuration, source or current authority is refused. Read `action_availability`: a cold observation can offer `stop` and guarded `retire`; the three-field selector still reports `successor` as unavailable. Use the separate version-two procedure below for a prepared successor. A callable resume still requires the ordinary workflow guards; this observation grants no permission for an effect.

3. Review the reported state and current human instructions. If continuation remains appropriate, change only `action` to `resume` and run the same command. A verified cold replacement uses a different actual owner process, follows signed routing in the original authority journal and preserves the original configuration and execution deadline. The controller decides the next eligible step. A human hold, reassignment, changed scope, missing review or uncertain effect may keep it blocked.

   Before any replacement execution, cold `resume` reads the selected task's retained provider operations and receipts under a separate 30-second capability. A known completed mutation is confirmed by its original identity and canonical readback without another send. A proven unsent operation can send only under the unchanged, still-valid original execution grant. Missing create identity or a lost label response without a saved effect response stays uncertain; do not search by title or repeat the mutation.

   Read each entry in `provider_recovery`. Comment, label and choice stages are separate: recovering a comment does not send a pending label, and a choice keeps its original human source and key. A completed effect claim is released only when its original forward binding proves that exact publication or choice has finished. Missing legacy claim facts remain protected. New publication intents bind their original task version and human state; an older intent without those facts cannot authorize a remaining send. Only the selected task's inbound receipts are drained, preserving received/applied identity across restart.

   If readback settles retained effects after execution expires or is revoked, expect `original_execution_unavailable`, a checkpoint and exit 4. This is useful provider settlement, not a new worker or execution permission. An `unsent` entry preserves journal evidence of no recorded send without rearming the operation under expired authority. `provider_reconciliation_pending` retains an unsent stage or uncertain effect. A changed enrollment, task version, human decision or ownership during readback stops dependent settlement. Preserve the result and original histories; do not renew the old grant.

   If initial preparation lost its enqueue reply before an owner was launched, repeat only the exact original enqueue request through the installed preparation port. The operator reconciles the original attempted status send without resending it. Preserve the original task version, decision, operation key, configuration and Writer journal/key. Missing history, an unsent mutation, a changed request or unrelated pending work keeps the call blocked. A successful provider-only readback does not demonstrate supervisor replacement.

   For code work, keep the original branch, dirty/untracked files, database, candidate and completed work units. Resume can continue the remaining check, merge and provider stages through this same command. New code plans bind their original merge/check journals before merge effects; missing or replaced stores and older plans without those bindings stay protected. Do not recreate them or copy a candidate into a new workflow.

   A pending commit with the new forward protocol marker can continue only when its component intent was never admitted and the original snapshot and execution authority still match. Known commit/publication effects use their original operation and actual repository evidence. Preserve unknown hook/publication outcomes for reconciliation. Completed author and reviewer stages remain recorded; a saved check is usable only for its exact current inputs. A committed Git publication can still have pending provider confirmation and retained cleanup obligations. Do not report those later stages as complete from the commit alone.

   To stop an interrupted worker after its owner is verified dead, use `action: stop` with the same workflow reference and key. Recovery records a stop intent, asks the original retained harness to stop itself and observes every applicable component before Core settlement. The result must report complete quiescence. Missing native, authentication, container, reviewer or merge facts keep the obligation blocked. A recorded stop fences later execution of that same workflow.

   After repeated owner replacements, keep the same request. Recovery checks the retained author and reviewer controllers against their original signed activations and the verified replacement lineage. Do not rewrite a controller record to name the latest owner.

   If startup stopped before component registration, the workflow's start result may still be pending even though Core committed a reservation. Use the same `stop` request. A confirmed pre-launch disposition reports the original attempt, `disposition: unlaunched_reservation`, `components_started: false`, and whether a runtime claim was recorded. Core pauses that original reservation without creating worker or stop receipts. Missing original forward evidence or any ambiguous launch history keeps the reservation protected; do not create a replacement witness or run another worker to resolve it.

   The same pre-launch checks apply to a configured reviewer through its own original reservation key and journals. The parent stop remains blocked until every reviewer and other applicable consumer is reconciled.

   If the interrupted start committed only its signed intent and Core has no reservation, use `resume` only while current execution authority still permits it. Recovery keeps the original decision, key, deadline and first-owner witness, and records the replacement's actual ownership separately. A committed or uncertain reservation cannot use this path to launch another worker.

4. Preserve the returned workflow identity and separate observed result. Repeating this request continues or returns its recorded work; it does not authorize another attempt or resend an unknown effect.

## Retire stopped owned resources

Use this local retirement procedure only after the verified owner and every related resource consumer have stopped. Keep the exact installed source, original configuration, installation, workflow reference and operation key. Preserve dirty or unmerged work, missing history, unknown effects and foreign metadata. A successful stop alone does not authorize removal.

1. Require confirmed current provider ownership, even for an already delivered task. Confirm the original resource ownership and quiescent outcome in the retained journals. Code resources also need trusted delivery or confirmed cancellation and commits retained by the configured release target. Preserve every original grant and revocation; retirement does not restore execution authority.
2. Set only `action` to `retire` in the original three-field request, then run the same installed `workflow recover` command. The explicit call admits a separate finite local observation capability. Expect exact-task checks and exclusive consumer coordination before removal. An active or ambiguous consumer, changed task, missing journal or changed physical resource stops removal.
3. Require `state: retired` and both resource dispositions `removed`. If the reply is lost, repeat the same original request. Recovery reads its durable removal intents and repository registration; it does not recreate resources or remove a replacement object. A missing path without original removal intent stays uncertain.

The command retains branches and coordinator journals. It does not archive provider fixtures. Those require their own current finite administration authority, recorded ownership, last-consumer checks and original cleanup key. Historical uncertain archive keys whose cleanup-phase authority cannot be refreshed remain protected; never amend an old deadline or resend an uncertain mutation.

## Admit a successor

Use this procedure after the original execution expires or is revoked and the owner, effects and resources have been reconciled. Preserve every original file, key, deadline, failure and revocation. A held, delivered, foreign or uncertain task cannot obtain a successor. T07 separately demonstrates genuine expiry and revoked-predecessor successor execution. Component controls retain their declared authored external-port limits.

1. Stage a separate private service configuration and unused owner/capability paths. Keep the original Core, authority, provider and Writer histories, repository, state root, approved write scope and required reviewer task identities. Use the normal sealed native inputs for the fresh plan; never copy or extend an old permission. Keep the original configuration and installation unchanged.

2. Through the trusted operator port, call `installation.sessions.successor.setup(fresh_config, original_config, actions=("successor", "start", "merge"), deadline=api_deadline, operation_key=enrollment_key)`. Select only the actions needed by the remaining work. This verifies the selected provider/account and stages a new token; it does not un-revoke or rotate the old Core session. After setup updates the fresh configuration, seal its fresh installation with that exact configuration binding, a distinct plan reference and a finite execution deadline within the API deadline. Keep enough separately bounded time for owned stop and observation.

3. Call `installation.workflows.successor.prepare(original_config, original_installation, fresh_config, fresh_installation, workflow_ref=original_ref, original_key=original_key, operation_key=fresh_key)`. Retain the returned signed intent reference. Preparation binds the original workflow, current task/version/decision and remaining work. Repeating the same prepared inputs returns the same reference. A changed request requires explicit reconciliation; do not overwrite a prior preparation.

4. Save this exact closed request in a private file, then run the ordinary installed recovery command against the original files:

   ```json
   {"version":2,"action":"successor","workflow_ref":"<original-ref>","operation_key":"<original-key>","authorization_ref":"<prepared-intent-ref>"}
   ```

   ```sh
   aitm --config <original-service.json> --installation <original-installation.json> --json workflow recover --input <successor-request.json>
   ```

   Expect `successor_admitted`, a distinct `workflow_ref`, the original `predecessor` and the fresh operation key. Compare those identities with the prepared intent. Admission starts no worker and sends no provider mutation. A refused or uncertain boundary leaves retained work protected. An expired recorded retry may report `successor_recorded`; that result permits history inspection only.

5. Before execution, verify the fresh normal native permissions, account/profile, installation and original finite limits. Launch the supported owner with the fresh configuration/installation and use the fresh task/plan/key through the ordinary installed `workflow run` command. Preserve the old key as historical identity. For partial work, require a distinct new attempt using the original owned files/database. For a completed worker, compare commit, candidate, review and check identities and counts to prove that only remaining stages ran. Current human changes, moving inputs, unknown effects and missing history must still block dependent work.

The predecessor remains history, including when its Core session was revoked. New Core authority expires independently within its fresh API bound; native execution still has its own tighter deadline. Do not renew the old session, delete writer fences or recreate a missing history file to make continuation possible. Reuse a saved judgment or check only when the guarded current inputs match its original source and provenance. Frozen publication must use original-effect reconciliation rather than another publication request. Retain worktrees, databases, candidates and journals for the separate retirement procedure.

## Confirm success

Compare the workflow/task/plan/key/deadline and existing attempt with the original request. Inspection must preserve attempt and effect counts. Resume must retain completed stages and produce the ordinary current result, including any required wait. For provider reconciliation, compare the original operation/publication identity with canonical readback and verify that known effects were not sent again. Compare inbound receipt and application records separately. Preserve unrelated comments/labels and every original choice/key. Verify actual Core/CLI/provider facts for the stage being claimed. A command's zero exit or a recorded step is not proof of business completion, provider execution, lead acknowledgement or human acceptance. The ordinary workflow client can return uncertain exit 6 after its 120-second forwarding limit while the owner continues. Preserve that result and use the original reference/key to inspect or recover; do not infer owner death, failed work or permission to launch another attempt. At publication, the inner Git receipt may already be saved while provider confirmation and outer workflow completion remain pending.

## If it fails

Retain the exact command, original identities, deadline, result and current observations. A missing reply may follow an effect; use the same reference and key to inspect the recorded owner before deciding the next action. Do not reset journals, launch an owner outside the recovery interface, signal recorded PIDs, remove endpoints by assumption, copy resources or renew old authority.

An unknown owner, missing original witness, changed file or unavailable component observation remains blocked. An expired or revoked execution grant cannot resume execution; the explicit cold provider pass can still settle known effects under its separate current observation authority. Keep retained work and resources protected when stop evidence is incomplete; a successful stop retains task worktrees, databases and original journals. The [workflow recovery Interface Contract (IC)](interface_contract.md) describes the current boundary.

## Prepare genuine interruption qualification

Genuine cold replacement/replay, active owned stop and current-valid cancellation fencing were independently assessed on 16 November 2026 for the selected Claude/default-account/Sonnet 5.5/high profile. The [Test Status Report (TSR)](../test_status_report.md) records the actual results and preserved verifier failures. The six steps below reproduce S1 qualification. For future qualification, start effects only after the delivery lead independently reviews the candidate and admits the exact fresh source, sealed inputs, account, scope and finite permissions. This admission is part of the already approved DP05 execution.

1. Prepare at most two fresh independent supported fixtures, one for replacement/replay and one for interrupted owned stop. Use the accepted default-owner route in the [DP03 handoff](../plans/deliveries/DP03-handoff.md), Supported procedure steps 1–2, with fresh original files, database, operation keys, resource roots and permissions. Select plain unmodified Claude CLI, the signed-in default account, `claude-sonnet-5-5` and high effort. Verify the actual current profile/account and authority before effects. Historical installations, grants and revoked permissions are evidence only. Bound each fixture to one author native call and a 450-second total qualification window. Set its original execution/owner deadline to at most 300 seconds inside that window, reserving at least 150 seconds for separate stop authority, automatic owner closure and observation. These bounds apply only to fresh v2 fixtures; the failed v1 preparation retains its original 300-second total and 180-second execution bounds. Any tighter actual native/session limits remain binding.

2. Install the exact candidate wheel with locked dependencies and verify installed runtime bytes against committed source. Enroll the fresh scope through `installation.sessions.setup`, using the approved actions and finite deadline. Prepare the supported native registration and sealed installation using the existing fixture machinery. Start `installation.workflows.launch(config_file, installation_file, stop=stop_event, ready=ready_callback)` in a real owner process. The callbacks may observe readiness or request ordinary lifecycle stop; they must not replace native/provider/recovery handlers. Confirm the authenticated scoped CLI before work.

3. Run the literal installed command `aitm --config <service.json> --json workflow run --input <run.json>`, where the private file contains exactly `task_id`, `plan_ref` and `operation_key`. Preserve the returned workflow reference, original key, task/plan/source/deadlines, physical store identities and attempt/effect counts. If the run reply is still pending, obtain only the exact recorded reference through `WorkflowStore.open_existing(...).find(scope, task_id, operation_key)`; do not invent one or create another run. In the replacement fixture, wait for an actual retained safe workflow boundary, such as a completed native result awaiting review. In the stop fixture, require actual forward-recorded native identity, a running Core attempt and its recorded active assignment invocation before killing the owner. Stop if either required observation does not occur inside the original bound; do not manufacture it.

4. Kill only the exact test-owned owner through the original subprocess handle, then wait for that handle to report termination. Preserve its PID/start identity and original descriptor/socket. Do not kill discovered numeric PIDs or delete endpoints. Use the original installed `workflow recover` command and three-field request from this guide: inspect first, then `resume` for replacement/replay or `stop` for settlement. The completed T02 operator must verify the old owner's death and current applicable authority; stop authority must not refresh execution. No changed config, renewed old permission, second reservation or second native call is allowed.

5. Require the replacement fixture to show a different actual owner PID/start identity, the original task/workflow/key/plan/source/deadlines and identical retained attempt/effect history, plus a usable original-key replay through the installed command. Require the stop fixture to show actual native, command, waiting-harness, collector and merge component facts wherever applicable before settling Core; unknown components retain uncertainty and capacity/resources. Exercise a current hold/cancel at the retained boundary and verify it blocks obsolete execution. Compare fresh provider/Core/CLI observations rather than accepting a command exit or safe refusal as S1 completion.

6. Close only the genuinely owned remaining processes through supported lifecycle/stop paths. After observed stops, revoke owned normal permissions with `NativeStore.revoke`, conformance enrollments with `CaptureEnrollments.revoke`, installed API enrollment with `SessionObservations.revoke` and its original Core session with `Core.revoke_session`. Use the original verified stores, enrollment and handle; inspect recorded revocation before retrying a lost reply. Preserve original grants and deadlines. Record actual worktree/database/provider disposition and retain dirty, shared, candidate, uncertain and foreign resources. Preserve failed commands, original source/permission/deadline bindings and every uncertain effect. Do not erase journals or repeat an unknown provider write. Stop before the admitted deadline if the required connection or evidence is missing; return the exact remaining boundary for continued T02 work.
