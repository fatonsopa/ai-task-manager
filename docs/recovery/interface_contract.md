## Scope and authority

The provider is the installed operator API, `installation.workflows.recovery.recover`, reached by `aitm workflow recover`. The consumer selects a recorded workflow through its original installation file and service configuration. That JSON file selects existing work; it grants no permission. The original live owner verifies the current enrolled session through its configured observation source. CLI and MCP retain the shared Core policy.

The signed owner-activation record captures the original installation file identity, workflow file identity and store UUID, and actual owner PID/start identity. New installation activations also bind the original Core, authority, runtime, host and configured provider/dependency/writing journals, keys and session file. The operator verifies these facts with the original authority key and current source/configuration. Cold composition opens current stores in existing-file mode, without initialization or migration. A missing or changed witness is a reconciliation blocker. Historical rows are not backfilled. Ordinary supported run/resume behavior remains available under its existing authority contract.

## Operations and messages

The operator command is:

```sh
aitm --config <service.json> --installation <installation.json> --json workflow recover --input <request.json>
```

`inspect` returns the recorded workflow/task/plan/key/deadline, attempt identity, current task version/decision/status/prose digest, recorded or pending step names, and the verified owner state. It creates no attempt or external mutation. A live-owner `resume` forwards the original workflow reference to the existing guarded owner. For a verified dead owner, `resume` evaluates retained reconciliation first. When the original execution checks permit continuation, it starts a different installed owner process under a signed replacement link in the original authority journal. The original config, installation, descriptor, stores, workflow, operation key, plan and execution deadline remain unchanged. Only that verified replacement lineage may retire the original stale owner socket. The ordinary client follows the signed link to the replacement; no copied configuration or new authority database is involved.

Before admitting execution, cold `resume` reconciles the selected task's retained provider operations under a separate 30-second observation/settlement capability in the original authority journal. It opens existing stores, binds the original enrollment and its existing revocation record, and rechecks those facts throughout the call. This capability may read canonical provider state and settle exact local records even after execution expires or is revoked. A later enrollment/revocation change stops that call. It cannot authorize a new send or execution owner.

Known outbound effects reconcile through the saved response or candidate identity; an update may use its original issue identity. Canonical readback must match the original operation and current task/version/decision before Core confirmation. Recovery does not resend these effects. A proven unsent pending or failed operation may send only while its unchanged original execution deadline and current enrollment remain valid. An unknown create identity remains uncertain; matching titles do not identify it. Separately authorized successors use the version-two boundary below; they do not rearm this original send. The initial installed preparation port also accepts the unchanged original enqueue request for readback when exactly that committed status send remains unfinished. It requires the original signed request, invocation, decision, task version and retained Writer journal/key; missing history is refused without recreation. This route performs readback only and cannot send an unsent mutation or select unrelated pending work.

Comment, label and choice stages remain distinct. Recovery reads the original comment identity and confirms its exact content. It does not send an unstarted label mutation. A lost label response without a saved effect response remains uncertain even when the label is present. A saved response permits canonical label readback, preserving unrelated labels. A recorded choice retains its original human source, request digest, option and resolution key; readback cannot invent a choice. Completed stages can release only an effect claim with its original forward-recorded publication/choice binding. Missing or ambiguous claim history stays protected and is never backfilled. New publication intents also capture the original task version, decision revision and human hold. Missing version facts permit only known readback, not a remaining send, and are never backfilled. Inbound replay consumes only the selected task's retained receipts and preserves their separate received/applied identities.

One call considers at most 32 outbound operations, 32 publications and eight eligible inbound receipts for the original task. The response's `provider_recovery` array reports original `operation_id` or `publication_id` and stage `state`, or the existing inbound result. An unknown effect returns `state: uncertain`, `reason: provider_reconciliation_pending` and exit 6. A journal-proven absence is reported as `state: unsent`; expired authority cannot rearm it. A remaining unsent publication stage blocks continuation. Successful settlement with unavailable original execution authority returns a checkpoint with `reason: original_execution_unavailable` and exit 4. These results describe retained provider progress, not completed work or renewed authority.

Execution after reconciliation still requires current same-session enrollment and the original unexpired native permission. It may release only a forward-recorded workflow claim belonging to the verified dead controller. A completed stage is reconciled from its original result and exact retained resources; it does not launch another worker. A changed task decision or uncertain external effect retains its blocker.

For code work, recovery retains the original worker branch, dirty and untracked bytes, database, candidate commit and completed work units. New code plans record the physical merge/check journal identities and store UUIDs before merge effects. Cold continuation requires those original bindings and opens the stores without initialization. Older code plans without them remain protected. A dead merge controller's claim transfers only after its original signed owner lineage is verified; the prior claim remains in its history.

A new worker-commit intent carries a forward protocol marker. If the component has not recorded its commit intent, recovery revalidates the original snapshot and may perform the remaining checks and commit under unchanged valid execution authority. An older pending intent without that marker remains uncertain. An admitted commit or publication reconciles through its original recorded operation and actual owned repository evidence; recovery does not blindly repeat hooks or external publication. Reopened candidates restore their original grant and exact check selection. Completed author/reviewer stages are retained, and saved checks are consumed only while their complete inputs still match. Frozen publication permits evidence consumption, not new discovery or checks. A proven Git publication and pending provider confirmation remain separate stages; retained resources still await independent retirement. Moving or divergent targets, foreign ownership, changed human authority and uncertain effects keep their existing guards.

`stop` is available through the operator interface for a verified dead owner with complete forward ownership facts. It records a durable stop intent for the selected workflow and admits a finite, separate stop capability. Cold observation and stop compose the existing Core and signed local sources without constructing a provider client or consulting execution enrollment. They still require every original physical store and signed identity. This capability cannot launch work, refresh enrollment or extend the original execution deadline. An original reservation is resolved through Core's committed operation and event history. Before Core settlement, recovery requires complete observations for native/authentication groups, the waiting harness, commands, collectors, reviewer attempts and any merge obligation. Unknown components retain capacity and protected resources. The stop intent fences later execution of the same workflow, including when a stop reply was lost. Current human changes remain recorded.

A retained author, reviewer or workflow claim may name an earlier owner in the verified signed replacement lineage. Recovery checks that controller's original activation, preserved descriptor, installation and physical source bindings, and confirms that the original process is no longer that owner. It preserves the original controller record; the latest owner does not replace its identity. An unrelated controller remains refused.

The pre-launch path requires an original signed `managed-reservation:` intent recorded before Core reservation. Recovery resolves the exact committed Core operation and event, confirms the dead controller through that same lineage, and holds the original runtime and host journals while checking related component intents, effects, observations and receipts. Any matching fact blocks this pre-launch path. Core independently requires the original reserved attempt with no worker, resource lease or checkpoint. It pauses that same attempt and records `reservation_stopped`; it creates no runtime attempt, managed-owner record, process observation or runtime outcome receipt. An existing runtime claim remains unchanged, and a missing claim stays missing.

The same pre-launch boundary applies to each configured reviewer. Recovery resolves that reviewer's own signed reservation key, task and committed Core operation, then checks its original physical runtime and host journals. It does not create a parent workflow start record for the reviewer. Every reviewer must establish this disposition or complete component-stop evidence before parent settlement.

When the original pending start has no committed reservation, a verified replacement may retry its saved intent under current execution authority. It verifies the original decision, task version, key, deadline and empty reservation history. The first controller's signed pre-reservation witness remains unchanged. A separate signed retry witness records the replacement's actual identity, followed by its ordinary managed-owner record after reservation and runtime claim. A known reservation, related runtime ownership or ambiguous history blocks this retry; it never authorizes another worker for a committed reservation.

A confirmed pre-launch response has `disposition: unlaunched_reservation`, `components_started: false`, the original `attempt_id`, and Boolean `runtime_registered`. The last field describes a controller journal claim, not a launched worker. This path is available only when the original forward witness exists. Older or incomplete reservations without it remain protected; recovery never backfills a witness. Related launch effects, observations, receipts or ambiguous history require the component-stop evidence contract and block this pre-launch disposition.

`action_availability` lists `inspect` and guarded `resume` as callable. A cold inspection also lists `stop` with `effect_eligibility: requires_complete_owned_stop`; a live-owner inspection retains its existing stop-unavailable result. A cold inspection also offers `retire` with `effect_eligibility: requires_stopped_owned_merged_resources`. The three-field selector still reports `successor` as unavailable; a successor needs the separately prepared version-two request below. Callability describes the interface and grants no effect permission.

`retire` uses the same three-field selector and original installation, workflow and operation key after verified owner death. It creates a separate 30-second local observation capability in the original signed journal. Core permits only exact-task retained reads under that capability, including when the original Core token is revoked; ordinary session resolution and writes remain denied. Task version, decision revision and prose identity must remain unchanged during removal. No execution, provider mutation or renewed enrollment is granted.

Retirement requires confirmed current provider ownership, including for an already delivered task, confirmed quiescence, settled related consumers, no unresolved merge or worker commit, clean worktree content, trusted delivery or confirmed cancellation for code work, and commits already retained by the configured release target. It pins the original consumer fence exclusively and verifies original physical worktree/database identities before removal. The database owner marker remains the original physical resource owner after succession. Missing ownership, journals, changed paths or metadata, active consumers and unknown outcomes retain resources.

Before each local removal, the runtime journal records its original exact resource intent. If its reply is lost, the same request reconciles an absent path against that intent and, for a worktree, its owning repository registration. Missing paths without such an intent remain uncertain. A replaced object is refused. A successful response has `state: retired`, the original workflow and attempt IDs, and `resources: {"worktree":"removed","database":"removed"}`. Original branches, coordinator journals and historical evidence remain retained. Provider fixture archives are a separate scoped administration boundary; `retire` does not archive an issue or project.

The closed request function in `installation/workflows/recovery.py` owns operator syntax. The public `workflow_inspect` schema in `application/service/models.py` accepts only `workflow_ref`; its handler verifies current same-session enrollment before and after observation. CLI `workflow inspect` and MCP expose that scoped read. They cannot mint recovery or successor authority. The existing trusted typed `WorkflowService.recover_expired(RecoveryAuthorization)` remains code-only and retains its narrow zero-effect contract.

## Data and validation

A version-one operator request has exactly three fields:

| Field | Required value |
| --- | --- |
| `action` | `inspect`, `resume`, cold `stop` or cold `retire`; version-one `successor` is recognized but unavailable |
| `workflow_ref` | Nonblank string, 1–256 characters, selecting an existing workflow in the configured scope |
| `operation_key` | Nonblank string, 1–256 characters, equal to that workflow's original operation key |

Unknown fields are refused. The request cannot contain commands, imports, arbitrary paths, proof objects, deadlines or permission claims. The installation must match its recorded physical path, source and configuration. Execution still requires its original finite future deadline. The explicit cold stop port can settle an expired obligation under separate current stop authority. Cold `resume` can separately reconcile retained provider effects before execution admission; neither capability can execute an expired or revoked grant. The selected task, plan and key must match saved history. A copied or rewritten installation cannot replace the signed original.

Example request, using illustrative identifiers:

```json
{"action":"inspect","workflow_ref":"workflow:recorded-id","operation_key":"original-run-key"}
```

The response uses the existing application envelope: `ok`, `outcome`, `data` or `error`, and applicable `exit_code`. Inspection returns facts, not business completion or human acceptance. A successful resume may still return the ordinary blocked/uncertain result of its workflow, including `awaiting_review`.

## Access and failure semantics

Current source, configuration, signed activation, physical stores, scope and original identities must remain valid. The original live owner authenticates its transport and rechecks current enrollment; caller-authored JSON cannot supply that observation. Expired, revoked or foreign enrollment cannot authorize execution. Separate operator observation/settlement and stop capabilities resolve only exact retained obligations. Task version, decision revision, ownership and enrolled source checks surround provider reads and settlement. Default configured outbound, inbound and publication consumers retain their current enrollment, configuration and claim guards; the explicit cold pass supplies its separate observation/settlement guard. Missing original history stays protected and is never recreated.

The existing envelope distinguishes invalid input (exit 2), denied evidence/authority (3), unavailable prerequisites (4), unclassified failed operations (5) and uncertain transport/effects (6). Unknown owner or component observations block dependent effects. PID reuse never grants signal authority. A cold caller sends no signal to a recorded numeric PID and constructs no replacement child handle. Version-one `successor` and live-owner `stop` or `retire` return unavailable results. The explicit version-two successor request has its own current authority checks.

Local records and external effects remain separate transactions. A missing reply is not rollback. The original key/reference select retained history; they do not authorize a second attempt or an uncertain external resend. No distributed atomicity or exactly-once external execution is claimed.

## Version-two successor admission

The trusted `installation.sessions.successor.setup` port stages a separate configuration and version-two capability file under fresh finite delegation. It retains the original Core, authority, provider and Writer stores, task scope and logical session. The old token is never transferred or reset; a revoked original session remains revoked. `installation.workflows.successor.prepare` binds the current task version, human decision revision, remaining work, required reviewer identities, new installed plan/key/deadline and original physical history in the existing signed authority journal. These Python ports are operator composition, not model tools or human-message evidence.

The installed selector accepts exactly these fields:

```json
{"version":2,"action":"successor","workflow_ref":"<predecessor-ref>","operation_key":"<original-key>","authorization_ref":"<signed-successor-intent>"}
```

`version` is the integer `2`; `action` is `successor`. The three references are nonblank strings of at most 256 characters. The request selects the original workflow/key and a prepared signed intent. It supplies no paths, commands, proof objects or replacement deadline. The signed intent owns the fresh operation key and plan. Missing, changed, foreign or ambiguous history refuses admission before dependent effects.

Admission requires a verified stopped owner, settled selected attempts and applicable reviewer consumers, reconciled provider effects and original owned resources. Current task/version/decision, human hold, issue ownership and enrollment checks remain binding. The existing workflow transaction publishes one current head and unique predecessor link while retaining the old body, steps, attempts, failures and keys. A separate Core commit exposes only the fresh finite task-family capability. If that commit is interrupted, an exact current retry completes the same admission; concurrent equivalent retries return the same successor. A conflicting request refuses. A recorded retry after expiry can return `successor_recorded` with `execution: authority_expired`; it grants no execution.

A successful response includes `workflow_ref`, `predecessor`, `state: successor_admitted` and the fresh `operation_key`. Admission creates no native process or provider mutation. Execution uses the separate fresh configuration, ordinary registered native permissions and bounded installed owner. The old key continues to select old history, and the predecessor cannot acquire another workflow claim.

A stopped partial attempt can continue on its original owned worktree/database under a distinct fresh attempt. Dirty/untracked files and original database ownership markers remain intact. A completed worker keeps its commit and completed units. A saved pre-publication code plan receives fresh linked merge authority; exact owned candidate, check and captured-review evidence can be reused without repeating completed stages. Original plan deadlines, capture expiries and judgment provenance remain history. Changed inputs or an unproved completed judgment refuse reuse. Frozen publication history and unresolved effects require their original reconciliation; they cannot become fresh publication intent.

The first admitted task capability enrolls successor writer protocol one across the operational Core tables. Scheduling/publication protocols 4/5 alone cannot renew an old session or write task state afterward. Historical SQLite reads remain possible; they do not grant API authority. Removing the capability table/fences, resetting sessions or rewriting old journals is not a supported rollback. Stores without successor enrollment retain their existing behavior. Version-one recovery and its ER01–ER10 controls remain unchanged. New owners open retained stores and keys without initialization; legacy rows do not receive fabricated witnesses.

## Forward-captured process and component facts

Production installation composition enables `ProcessRuntime(..., recovery_directory=...)` and consumes `adapters.process.recovery.stop_waiting(journal, attempt_id, check_authority=..., timeout=4)` behind the typed `ColdRecovery` capability. Reviewer composition uses the same retained harness channel. This channel is part of the accepted S1 boundary; T03 does not expand process-stop authority.

Launch records a private stop endpoint, secret and worker-source hash before creating the waiting harness. A private inherited file descriptor supplies the secret to that original process. Readiness records only the endpoint's physical identity. The secret stays in controller storage and inherited input, outside argv, readiness, public stop results and workflow inspection. Controller storage and endpoints remain outside the model's confined workspace and managed tool surface. The callback is an internal guard over the signed current stop capability, not caller-authored evidence or an execution grant.

The original harness accepts only authenticated `stop` requests bound to its attempt and actual PID. It stops its own process group. Losing the original owner before a work grant leaves this optional harness fenced until its original deadline or a valid stop; it cannot receive a new work grant through the stop endpoint. The default runtime retains its prior behavior. No historical launch is backfilled with a channel.

The cold caller checks original launch, process, source and endpoint observations, then observes the recorded group without recreating child handles or signaling a numeric PID. Unknown inventory, changed/reused identity or missing observations stays uncertain. A successful acknowledgement is not quiescence: a separate full-group observation must establish no live members. The result is one `cold_harness_stop` observation, reused on retry after a fresh absence check. It establishes neither model success nor native, command, collector or merge settlement. No Core capacity or resource is released here. The timeout is a finite observation/request budget of at most four seconds; an individual process inventory has its existing two-second bound. An expired or raising authority guard prevents the next control/settlement step.

Managed admission records the actual controller identity before starting components. Signed host facts capture native relays and authentication processes as they are observed. Container watchers retain a separate per-job cleanup signature; a cold caller checks the original signed watch binding, watcher-group absence and cleanup signature before using a lost cleanup reply. Native accounting settles known process stops through its existing controller port without resolving execution permission. Forward reviewer state facts bind each separate runtime and key to its original installation. Pending or uncertain merge ownership remains protected.

Selected checks in `tests/runtime/test_cold_harness_stop.py` cover an actual killed owner and original waiting process, replay, malformed/forged requests, refusal, unknown/reused identity and a foreign process. `tests/workflows/test_cold_operator.py` exercises different actual owners and a stock CLI with explicit authored provider/native ports. Those controls establish component behavior; they are not genuine Claude/account/provider execution. The finite genuine S1 procedure is in the companion How-to Guide (HTG). Actual installed qualification and its preserved failed verifier are reported in the [Test Status Report (TSR)](../test_status_report.md); future qualification still needs fresh finite admission.

T04 component controls include `tests/merge_workloads/test_cold_recovery.py`, the affected merge/worker-commit/code-policy controls and `tests/workflow_installation/test_cold_code_cli.py`. They exercise actual controller death, retained local Git/check evidence, the literal noneditable installed original-key route and unchanged native invocation history through authored provider/native ports. Independent T04 assessment accepts this component scope. The installed positive preserves one completed unit while finishing remaining workflow stages; a multi-unit subset is not demonstrated. These controls do not establish genuine S2 provider/model execution, which remains T05.
