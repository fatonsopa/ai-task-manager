# Queue observation and selection contract

Type: Interface Contract (IC). Status: implemented DP06 observation, admission and concurrent-delivery boundary; candidate-bound acceptance and genuine evidence remain separately scoped in the [DP06 handoff](../plans/deliveries/DP06-handoff.md). Sources: R07/R11/R15/R27, the approved [Implementation Plan (IP)](../plans/deliveries/DP06.md), `application/service/models.py`, `application/service/queries.py`, `application/scheduling.py` and the native lead composition under `src/ai_task_manager/`.

## Scope and authority

The configured application service provides queue observations. CLI, MCP and the ordinary managed lead consume the same scoped Core facts. Service schemas own request syntax; the implementation's typed projection owns response semantics. This contract describes observation and selection, not a second scheduler, new public scheduling command or permission to execute a model-selected task.

The installed dependency integration supplies current complete provider observations. Core alone decides readiness, ordering and admission. The operator's trusted installed plan selects the permitted workflow, resources and target; models cannot supply replacement ownership, commands, proofs or authority.

## Operations and messages

| Consumer | Operation | Input and result |
| --- | --- | --- |
| CLI | `aitm --config CONFIG --json task list` | No request fields. Returns the current session's visible task projections in admission order, followed by other visible tasks. |
| CLI | `aitm --config CONFIG --json task show --input REQUEST` | Exactly `task_id`, a nonempty opaque string up to 256 characters. Returns one authorized task projection. |
| Application service / MCP | `task_list`, `task_show` | The same closed input schemas and structured result envelopes as CLI. Unknown request properties are refused. |
| Ordinary managed lead | `task_list`, `task_show` | These existing read operations are selected from the sealed lead installation before native tool negotiation. Native permission, active account/model/startup, current provider enrollment and gateway scope remain required. |
| Event-only reporting lead | Existing sealed event operations | A configuration with `reporting_ref` does not expose task reads. It cannot become an ordinary queue-reading lead by supplying another task identifier. |
| Trusted operator | Existing `workflow_run` / `workflow run` | Exactly `task_id`, `plan_ref` and `operation_key`. CLI `workflow run` uses `--config` and `--input` through the retained owner; `--installation` belongs to the dedicated owner, lead-report and recovery commands. Rechecks admission and starts only through the installed workflow. Lead selection is neither a reservation nor worker-start authority. |

The success envelope contains `ok: true`, `outcome` and `data`. A list also reports `quarantined_count`; foreign or quarantined prose is excluded. A `task_show` request for another scope is denied. Task and workflow IDs are opaque; titles and display identifiers do not grant access.

### Explicit provider merge milestones

The sealed `linear` configuration and initial session manifest may include `dependency_milestones`, a list of at most 128 objects. Each object has exactly `task_prose_digest`, `predecessor_prose_digest` and `condition: "code_merged"`. Both digests are distinct lowercase SHA-256 values identifying approved task prose before task creation. Repeated pairs, unknown fields and other conditions are refused. Omission or an empty list preserves the existing `work_done` meaning for every provider edge, including its production-proof requirement for code work.

A declaration does not create a provider dependency or supply completion evidence. The real provider source must observe the edge and resolve exactly one current task for each approved digest in the same scope; the predecessor must be code-bearing. Missing or ambiguous tasks, non-code predecessors and absent provider edges are refused. Core still verifies the original current merge proof, approved prose, completed work, synchronization, quiescence and human holds before release. A delivered predecessor's status alone cannot release work. Explicit policy is part of the source identity, so changed declarations cannot reuse a prior operation receipt or reset an existing dependency graph.

Before Core consumes an explicit merge milestone, the provider observer asks the exact closed predecessor member to re-prepare its original merge reference. The producer reads that member's completed scoped workflow head and witnessed candidate, check and publication history; a cold composition reconstructs those existing consumers. It rechecks current source, ownership, checks and target ancestry without repeating an author, review, check execution or publication. The stable reference keeps its five-second lifetime; each new observation requires fresh original-producer preparation. Already delivered check reads may accept a target descendant only when the exact recorded quiescent publication and original candidate ancestry remain verified. Pre-delivery target checks remain strict. Core verification performs no provider collection or Git command.

The existing native startup and running observers also maintain these local witnesses between provider collections. They select the current task’s declared merge milestones before resolving a provider receipt; a declaration for another task does not require local milestone preparation. For a declared subject, they use the signed receipt matching the current Core-published observation, including its scope, task, source, revision and original expiry. A cached reference cannot authorize an older or superseded observation.

Collection records the provider observation time and its original 30-second expiry before subsequent local milestone work. The shared preparation path then revalidates or re-prepares expiring local merge witnesses through their original current issuer, preserving their five-second lifetime and the provider receipt's timestamps. Native startup and stopped-worker delivery consume this same path. Task/predecessor ownership, source, holds and receipt expiry remain checked around local preparation; Core still verifies the witness when starting the worker. Replaying a sealed receipt repeats the required current local verification, including after an earlier preparation refusal, without another provider read or an expiry extension. Replay uses the original provider expiry rather than restarting the collection budget.

Same-task collection, Core publication and local milestone preparation share a bounded producer boundary outside Core transactions and model guards. Separate source instances using the same physical receipt store share that task’s boundary; independent tasks retain separate boundaries. A completed newer observation may supply its current signed receipt after normal Core publication. An unfinished collection does not replace the published observation. Cancellation, current holds, changed source, invalid signatures, superseded receipts and expired provider or execution authority remain binding. Local proof preparation performs no additional provider polling and does not advance provider receipts, revisions or deadlines; ordinary verification retains its existing local checks.

The ordinary installer, owner and same-source cold replacement read this configuration through the same `LinearComponents` composition. Keep it sealed before enrollment; changing a live configuration does not renew or extend its authority. `tests/scheduling/test_provider_source.py` covers configured release and refusal boundaries; `tests/session_observations/test_operator.py` checks manifest preservation. These authored controls do not establish genuine dependent delivery or interrupted recovery.

### Closed concurrent task membership

A trusted version-one worker installation may add `task_installations`, containing one to sixteen exact file bindings with `path`, `device`, `inode` and `sha256`. The maintained syntax is `installation/workflows/schema.json`. Omitting the field preserves the single-task installation. Each bound child must be a worker in the same configured scope, with the same original finite deadline, a distinct task and plan reference, and a separate state root. State roots cannot contain one another. Children cannot contain another task roster. A copied, replaced or edited child binding is refused. The roster is sealed before the owner publishes readiness; ordinary workflow requests cannot enroll another task.

The existing owner serves these closed members through its existing request pool and task locks. The canonical Core, session and authority remain shared. Each member composes its own workflow journal, runtime/host journals, worktree resources, process runtime and application database. A run or resume selects that task's installed context; it does not reuse another task's native permission or resource identities. Current dependency, human, capacity, resource, source, account and permission checks remain binding. Inspection observes recorded state while other task requests execute. Same-key replay keeps its original task/workflow and does not start another attempt. An overlapping run or resume for an already-owned task returns blocked, with exit 4 and `Current task request is still owned`. Preserve the original key/reference and retry after the active call releases its task lock. These requests do not wait in the owner pool; task and workflow inspection can use the remaining handlers.

The signed activation records each member's original installation, workflow store UUID, physical journals and actual owner identity. `workflow recover` accepts the original root installation and selects the member containing the exact workflow reference. The original operation key must match that member. Cold inspection and stop retain their existing separate authority. Cold execution still needs current original execution authority and the unchanged deadline. A replacement reopens the witnessed roster in existing-file mode; missing, replaced or unknown-schema history is refused without initialization or migration. Before publishing replacement readiness, recovery may release one unambiguous sibling workflow claim only when its task, plan and controller exactly match that member's original signed witness and the proven-dead owner instance. It rechecks original files before release. Unknown, live or foreign controller claims remain protected. This releases a local workflow lock; it does not settle task/effect state or grant another member permission to retry retained effects.

Closed members share milestone verification only for `workflow-review:`, `code-worker-review:` and `merge-publication:` references. Exactly one current original issuer must own the prepared reference. That issuer retains its task, scope, freshness and physical-witness checks; a different subject or scope is refused. Code-unit re-preparation selects the actual current issuer. This permits explicit non-code unit/completion and code unit/merge dependencies without changing runtime, provider or decision proof routing.

`tests/workflow_installation/test_concurrent_owner.py` covers overlapping installed workers, distinct resource identities, responsive reads during duplicate requests, same-key replay, closed-member refusal and original-key member recovery, including exact dead-owner versus foreign/live sibling claims. `tests/workflow_installation/test_member_evidence.py` checks the three milestone families and current dependency readiness. Its review captures and prepared merge observation are authored controls; they do not establish genuine model/provider concurrency, merge execution or performance acceptance.


## Data and validation

The `scheduling` object accompanies the task's actual `observed_status`, `sync_state`, `human_hold` and execution facts. Its fields are observations, not caller-set parameters.

| Field | Meaning |
| --- | --- |
| `state` | Dependency readiness: `ready`, `blocked` or `unknown`. This does not reserve capacity. |
| `blockers` | Dependency/source blockers with a machine code, authorized dependency identifier or null, and release condition. Foreign predecessor identifiers are not disclosed. |
| `task_version`, `graph_version`, `source_revision` | Bind the decision to its task and dependency observation. Unknown source revisions remain null. |
| `priority`, `queue_sequence`, `expires_at` | Current declared priority, original explicit queue order and receipt expiry. Missing observations/order remain null. |
| `selection_state` | `ready` for the first selection-eligible task, `waiting` for another eligible queued task, `blocked` when selection is unavailable, or the recorded active attempt state. |
| `eligible_since`, `wait_seconds` | Start of the current continuous eligibility epoch and nonnegative elapsed wait, using the configured Core clock in seconds. Both return null outside a current eligible waiting epoch. Ordinary installations use the same clock basis as dependency expiry. |
| `bypasses` | Nonnegative count of committed later-queued higher-priority admissions during that epoch. Failed capacity/claim attempts and replay do not increment it. |
| `fair_turn_due` | True when a currently eligible task has at least four counted bypasses. The oldest qualifying waiter has precedence among promoted tasks. |
| `waiting_reason` | `fair_turn`, `priority_order`, `resource_conflict`, `resource_declaration_unavailable` or null. Read it with readiness, hold, synchronization and ownership facts; it is not a complete independent authorization verdict. |
| `admission_requires_capacity` | True: selection remains subject to atomic capacity and other current admission checks. |

Routine observations and restart preserve a still-valid waiting epoch. Expiry, dependency loss, changed approved work or a current human hold ends it. Higher priority does not preempt an active attempt. A failed/canceled/held/missing/foreign or ambiguous predecessor is not success; only the declared verified unit, merge or complete-work milestone can release its dependent task.

### Declared resource admission

The trusted workflow installation may include `resource_locks`: an explicit array of `[kind, name]` pairs, where `kind` is `migration`, `test` or `resource`. An empty array is a known empty lock set; an absent field is unknown and cannot authorize a new admission. The sealed `files` array supplies literal repository-relative file claims. File/directory path collisions conflict; this interface adds no wildcard expansion. The installer binds the physical Git common directory, task, approved prose, current decision revision, original finite deadline and sealed source files. Models cannot provide these declarations through `workflow run`, `worker start`, CLI or MCP request fields.

Core claims the task, finite host/project capacity and declared resources in its existing admission transaction. Claims use the existing resource leases. Competing file, migration and test claims are checked within the same physical repository; named `resource` locks also conflict across repositories and projects on the shared store. A conflict returns the generic occupied-resource cause without another owner's identity or prose. An occupied queue head waits while compatible independent work can advance. A rejected claim or exact-key replay does not increment committed fairness counters.

Trusted setup records validated resource facts in the existing Core event stream. Ordinary service and lead readers can consume that task-scoped projection while checking its task/prose/revision, original deadline and sealed-file witnesses. Public event payloads report only that resources were declared; repository identity and sealed-file witnesses remain in the private Core audit record. That observation grants no execution: reservation and startup require the currently configured live declaration source and the exact atomic claim. New queue causes are `resource_conflict` for occupied resources and `resource_declaration_unavailable` for missing or stale facts. Provider workflow status is preserved.

The admission lease remains owned during active or unknown execution. Confirmed quiescent execution settlement releases its admission claims; existing physical resource/check/merge consumer controls continue to govern later use and retirement. An active legacy attempt without the new declaration marker is unresolved ownership, not a known empty declaration. It blocks competing admission, and an original-key reservation replay alone cannot launch a replacement. The supported original unlaunched-reservation stop may release its logical marker only after its existing independent zero-effect observations pass.

Core schema 6 reuses the existing forward-writer fence. Migration retains the original before-image, operational rows, unknown attempts, keys and physical resource facts, and replaces the writer epoch atomically. Earlier fresh openers and preopened connections cannot write through the new fence. No old declaration is invented. Legacy plans without `resource_locks` retain their original digest and completed replay history; new work needs a current complete trusted installation. Do not edit an enrolled installation or renew old authority to manufacture compatibility.

## Access and failure semantics

Every call requires the sealed configuration and currently authorized session. Native queue reads additionally require the ordinary lead's current role, permission, source/profile/account and configured gateway. Queue reads grant no file, command, worker-start or authority-minting capability. Event-only reporting remains confined to its original event and receipts.

Worker and reviewer file operations distinguish creation from updates. `create_file(path, text, operation_key)` creates only an absent path and atomically refuses an existing file, including one published concurrently. `write_file(path, text, expected_hash, operation_key)` retains its required nullable hash field; omitting it is invalid. Use the observed hash for an update. Both operations use the same current lease, model, resource, human-decision and original-deadline checks and share the edit operation-key namespace. An existing or uncertain edit intent cannot authorize another publication. Worker qualification covers explicit creation, a valid hash update and refusal to create an existing path within its thirteen-case matrix. The five-case lead matrix and its file-write exclusion remain unchanged. The new worker tool surface requires a matching capability profile and capture; prior task grants are not transferred.

Reads do not start workers, reserve capacity, advance wait counters or change provider workflow status. Selection is not atomic with a later operator request: the workflow rechecks all current guards. Provider/network observation and process/resource effects occur outside Core's short admission transaction.

Public failure categories and CLI exit codes remain those in `application/service/models.py`: invalid input 2, denied 3, blocked 4, failed 5 and uncertain 6. A lost run response may follow an effect; preserve the original key/reference and use supported reconciliation. Do not infer rollback or exactly-once external execution from a local query or idempotent reservation.

Candidate checks retain a successful, stopped physical execution separately from a later source or authority refusal. The check remains unknown, with no reusable pass, and records bounded redacted failure metadata. A positively identified target change also binds the exact check plan, candidate commit/tree, source, grant and expected/observed target. Only that complete record can produce the public blocked reason `candidate_target_moved`. An original-key continuation then rechecks current authority, holds, source, resources, target ancestry, publication state and the existing attempt/deadline limits before preparing a new candidate and running fresh checks. It preserves the original author work and prior unknown result. Generic unknown, source and authority failures retain their refusal; a later target read cannot reclassify an older unknown check.

Initial Claude authentication uses a separate finite admission scope while its original counted host parent is `launching`. The existing native store may wait only for SQLite writer acquisition within the original auth, host and permission deadlines. Waiting consumes that window; the auth child cannot gain a later deadline from contention. The original permission and exact parent binding are checked again after acquisition. The protected body runs once; ordinary effect acquisition retains its 0.1-second fail-fast policy, and identity refresh still requires a `running` parent. Cancellation, expiry, revocation or changed ownership refuses the next admission. This scope grants neither worker readiness nor a successful account observation. Unknown process or stop facts remain protected and require supported reconciliation. A confirmed stop for the exact existing auth child is recorded through its separate bounded settlement policy even if admission was revoked, expired or canceled after launch. This records that observed child stop; it grants no new launch and does not clear an unknown process or parent obligation.

Normal admission reads the durable capability enrollment from its separately bound native store. Only acquisition of its coherent writer may wait. The wait is bounded by the original role and established host deadlines, the current initial-auth or running-identity window and its cancellation signal, and any earlier capture validity deadline. An absent capture expiry does not remove the role deadline. A preliminary read can only shorten this wait; it cannot authorize admission. The writer still checks physical identity and moved-file coherence, and admission rechecks the current task permission after reading the capture. Waiting renews neither the capture nor task, account, role or execution authority.

For an explicitly confirmed owned host stop, accounting reads the original calls through a bounded coherent snapshot and settles each issued call through its original persisted binding. The original invocation and permission deadlines bound contention; admission revocation or expiry does not erase an independently known stop. An observed model-turn completion uses that same issued-permit settlement path. An unknown turn or unconfirmed stop retains its unresolved obligations; a missing stop fact is refused. Neither settlement path repeats model input or establishes genuine delivery or concurrency.

Before managed startup asks Core to consume its original readiness proof, the native host acquires its existing current-observation guard outside Core. Acquisition is bounded by the original signed startup expiry, host deadline and owned process cancellation. The original startup record is read before entering Core; Core then rechecks the prepared owner, source metadata, model, current process and task authority while the guard remains reentrant for that caller. A direct Core caller encountering another thread's guard still receives an immediate refusal. Waiting creates no replacement startup, authentication or model input, and no new deadline. Cancellation, expiry, changed source or owner, known model refusal and unknown process state still prevent admission. This serialization does not establish genuine work overlap or settle another delivery failure.

Initial authentication and running identity acquisition may also wait for a preliminary snapshot when SQLite reports a confirmed busy or locked condition. Only that zero-effect read acquisition is retried, within the original parent, permission and identity deadlines and cancellation signal. Other database errors remain refusing. The provisional snapshot grants no execution authority: current parent and permission checks and the full coherent writer validation still follow acquisition. Ordinary effect acquisition retains its existing fail-fast policy. Expiry, cancellation or changed ownership still stops the next admission; shutdown and the matching successful native turn requirement are unchanged.

During an assigned worker or reviewer turn, the transport runs full source, provider, resource and inspection preparation before acquiring the root accounting writer or model effect guard for each native input frame. Inside those guards, the reviewer checks its prepared physical witnesses and the delegate’s current Core work lease, including the current author check before and after the effect. These current checks do not start provider collection or reacquire its publication boundary. A human hold, reassignment, changed source or inspection, expired authority, stopped process or model refusal still prevents the frame from completing. Root accounting, model and final-frame commit boundaries remain required; an incomplete or failed input keeps its original stop and reconciliation obligations. This separation grants no new tools, deadline or permission to repeat a review.

## Delivery and recovery consumers

The managed worker consumes only its sealed task’s tool and path authority. `create_file(path, text, operation_key)` expresses explicitly authorized new-file intent: publication atomically refuses an existing target without truncation or overwrite, including a target created during the call. A successful prior read is not required to request creation. `write_file` retains required nullable `expected_hash`; updates require the actual current hash, explicit null retains the existing expected-absence check, and omission is refused. Both operations retain shared lease, human, resource, deadline, scope and idempotency guards. The additive creation tool does not permit another task’s paths or bypass a held task.

At the candidate-check boundary, the owner retains verified stopped physical execution before final source validation. A failed post-check guard cannot create a passing check. The public `data.reason: "candidate_target_moved"` remains limited to the bound successful-stopped physical-check case after non-target safeguards pass, with exact plan/candidate/source/expected-versus-observed target. A nonzero physical result remains retained unknown/failure and cannot qualify.

A zero-dispatch group has a separate internal path. Exact typed target refusal is validated against its check plan before the group records only already-verified carried results or empty `skipped` with `physical_count: 0`. The workflow captures that exception inside immutable preparation and exits the preparation scope normally, restoring the original repository turn. The workflow matches canonical candidate/check-plan, current grant/source and expected-versus-observed target before using its existing same-key target replan, within original attempt, deadline and cumulative-wait limits. Unknown groups still refuse. This path creates no physical execution, new public reason or caller-supplied no-effect proof. Both paths preserve completed work and resolve required candidate checks before publication without author replay. Eligible physical-origin passes may carry under matching current unit/input/catalog/binding/producer/source provenance; stale or unbound passes refuse. Generic unknown, source, hold, resource or authority refusals remain blocked; old unknown records are never inferred to be target-only from a later read.

For an actual registered check unit, source/target checks remain strict before dispatch. Once that existing job’s nonce send/flush has returned, only a positively typed target change may be deferred while capturing that unit’s actual verified terminal/stopped result. Every non-target plan/catalog/source, human, resource and current-authority guard remains active. Another unit still requires strict validation before dispatch. A partial or missing physical result does not become a pass; previously unknown results remain unknown and cannot be replayed or reclassified from this correction.

After immutable preparation, an unchanged source with a moved target may enter the existing bounded same-key target successor only before publication intent/fence/effect and after current readiness revalidation. Canonical candidate, check provenance, unknown-group refusal, original replan count, deadline and cumulative-wait limits remain binding. Source changes and already-recorded publication stages retain their refusal/reconciliation rules. This internal continuation adds no public reason, schema, caller authority or deadline.

Ordinary cold execution retains its original task/workflow/key and finite deadline. Only verified cold recovery can prepare the internal completed-delivery proof for an exact done attempt with a durable stopped pending-commit receipt. The dependency consumer may collect current facts and use the existing completed-delivery checkpoint when the ready graph matches the original attempt’s graph, source, prose and decision. It preserves `invalidated_by` history and checks current enrollment at consumption. This is delivery of already completed work, not ordinary task admission or a wider successor privilege. Missing proof, changed graph/source/hold, unknown physical/publication state and expired original authority refuse. Fresh ordinary recovery routes that do not need this bootstrap retain their existing behavior.

The [recovery Interface Contract (IC)](../recovery/interface_contract.md) owns exact recovery schemas, bounded redacted diagnostics, stop/retirement and version-two successor eligibility. The [lead reporting How-to Guide (HTG)](../lead_reporting/how_to_guide.md) defines supported setup, exact-event publication and ordered receipt semantics. An owner-independent event-only enrollment requires the original still-valid Core capability and retained physical history; it grants no queue reads, worker start or business mutation. Reporting cannot restore a revoked Core capability. Keep that capability until the final event consumer is complete, and distinguish a fresh finite reporting phase from renewal of a failed one.

## Compatibility and verification

Queue fields are additive response data. Existing closed request schemas, task statuses and run/resume keys remain unchanged. Callers can ignore added response fields; selection uses current task/source observations rather than cached titles or row positions. Native launch and authenticated startup verify the exact installer-selected tool set; missing or extra tools still refuse.

`tests/scheduling/test_installed_queue.py` checks literal installed CLI and real MCP stdio agreement, blocked predecessor/hold handling, signed authored milestone release and four-admission fair ordering against Core admission. `tests/native_installation/test_lead_queue_reads.py` checks the configured lead boundary, malformed/foreign/worker-action denials and cross-role negotiation. These controlled cases retain authored provenance. Genuine lead selection, actual worker start, concurrent delivery and performance require their separately bound observations; neither schema conformance nor passing controls establishes those outcomes.
